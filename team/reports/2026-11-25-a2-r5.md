## 1. Configuration naming (scripts/import.py, do_generic)
- Cause: a configuration took `par.name`, the model's first marketing alias. Aliases carry no sku, so the fix binds each one through the configuration's
  own gen.capacity claim. New `own_alias(pr, sku)` picks the first marketing_name that states exactly one GB/TB capacity equal to that claim (+-3%).
  With no capacity claim (laptops) or no matching alias, the name falls back to the model's, as before. That is about 20 lines.
- Before/after: two full scratch imports from the same code snapshot. The only difference is import.py. Of 13,485 entities, **407 configuration names changed**, all SSDs:
  WD/SanDisk 175, TEAMGROUP 157, Samsung 38, Kingston 37. No ids, entities or claims changed.
  Example: team-tm8fgq512g0c129 'G50 EVO M.2 PCIe 4.0 SSD 4TB' -> '... 512GB'. wds200t5g0a '... 250GB' -> '... 2TB'.
- The Kingston workaround (a capacity-free model name first) is **kept**. It still gives the capacity-free model name, and configurations now get '<title> 4000GB'.
- Remaining: 18 of 584 SSD configurations still have a name capacity that disagrees with their capacity claim. Most are WD OEM parts (SDEQNRG, SDEPNSJ,
  SN810): one base Model Number covers several capacities, so one entity carries more than one capacity. That is an identity issue in sandisk_ssd (A2-ssd), not naming.
- Tests: new tests/test_a2_r5.py (11 cases: team / sandisk / kingston shapes, TB=GB, range alias, retail_slug, other sku).
