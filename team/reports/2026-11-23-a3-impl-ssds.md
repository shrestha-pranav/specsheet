# A3-impl: SSDs (category #4) integrated (2026-11-23)

## Decisions / open questions first
- **Unmapped premise was wrong**: SSD adapters had 0 unmapped claim keys (all keys already in spec-profile.yaml). The 1,636 `unmapped_rows`
  are laptops 97 / monitors 1,536 / power-strips 3 (source labels not mapped by those adapters). Count is unchanged (1,636 before and after); not an SSD defect.
- **One configuration scheme: `mfr_sku`** (importer, laptops/monitors, record schema pattern which does NOT allow `mfr_part`). Adapters no longer emit the `mfr_part`
  alias; profile configuration level + schemes use `mfr_sku` (package level = gtin only); `package_markets: mfr_part` removed from category.yaml (importer only reads `mtm`); identity.md updated.
- **Speeds conditioned, not separate**: adapters emitted a standalone `perf.cache_state` claim and left seq speeds unconditioned. Now `perf.seq_read/seq_write`
  carry `conditions={cache_state: in_slc_cache}` (the profile headline_condition) via `_ssd.add`; the qualifier claim is gone (1,035 conditioned speed claims).
- **Temp range fix**: `therm.temp_operating` was a `[min,max]` list (normalised 0 of 442); now `{min,max}` -> accepted.
- **Adapter version NOT bumped** (still @1): snapshots are selected by `adapter@version`, a bump would orphan them / force refetch. Nothing was published with the old parse.
  Gotcha: `raw/*/parsed/` is a cache; after editing a parser run `python3 -I crawler/adapters/<id>.py parse` (done for the 3), `--reparse` does not rewrite it.
- **Coordinator: confirm the two policies** (below), esp. accepting "up to" speeds as conditioned claims.
