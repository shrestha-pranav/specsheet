## 2 Semantics (resolve.py, normalize.py, adapters, profiles)
- An assertion is (value, qualifier, basis conditions, measurement mode), sorted canonically, so results do not depend on claim order. The resolution rules:
  - one assertion -> known
  - same basis/mode with different value or qualifier -> conflicted (so exact 100 vs "up to" 100 is a conflict)
  - only the basis/mode differs and the value is equal -> known, with per-basis alternatives
  - only the basis/mode differs and the values differ -> unknown + note + alternatives
- Headline, alternatives and conditional rows all keep qualifier, display, basis, mode, claims and sources (record.schema.json is extended).
- Profile `basis_conditions` qualify an assertion without splitting the headline. ES `power_basis` covers pwr.typical/standby; DisplayHDR `cts_version` covers hdr.vesa_tier;
  SSD `cache_state` covers seq read/write. The SSD headline_condition is removed: "up to" now gives `qualifier: up_to`, and `cache_state` is attached only on textual
  evidence (5 Samsung TurboWrite claims). normalize.py recovers a leading qualifier from the literal of a number the adapter already parsed.
- Publisher: an entity whose only trusted values are unknown + alternatives keeps its row and file (public ids stay).
