# specsheet visual system

## Authority and direction
The UI v1 brief governs this design. The incumbent's compact system-type table is useful visual authority: expand its information architecture and finish, preserving density and direct controls. This is an Operate/Read product, built directly in code. No images or decorative mockups are needed. The brief explicitly requests non-interactive design and implementation, so its supplied context replaces skill interview/confirmation rounds.

Readers compare products at a desk in daylight and revisit specifications on phones at night. Default to OS light/dark preference and offer an explicit persisted theme choice. Light surfaces are cool white and mist; dark surfaces are slate. Teal indicates actions and selection; amber indicates uncertain or conflicting evidence. Text labels always identify state.

## Tokens
- Light: background #f4f7f7, surface #ffffff, ink #172d32, muted #52656a, rule #cbd7d9, accent #006b67, accent-soft #e3f2ef, warning ink #805000, warning surface #fff3da.
- Dark: background #111c20, surface #19292e, ink #edf4f4, muted #adc0c5, rule #3a5057, accent #80ddd0, accent-soft #203f3c, warning ink #f5cf84, warning surface #3b3020.
- System UI sans for all navigation and prose; native monospace only for identifiers and literal technical data. Table numerals tabular. Body 15px/1.5; table 14px/1.45; h1 30–36px/1.15; section heading 20px. Avoid eyebrow labels and oversized hero type.
- Spacing: 4, 8, 12, 16, 24, 32, 48px. Max content width 1440px, gutters 32px desktop / 16px phone. Controls minimum 40px high; 44px touch affordances. Subtle 6px control radius; tables and document sections use rules rather than cards. No decorative shadows or gradients.
- Focus: conspicuous 3px accent outline with offset. Underline links in prose; buttons have visible hover/disabled states. Theme selection, caret and scrollbar. Reduced motion respected; only a short background transition on compare selection, no entrance animation.

## Components and layout
Compact masthead: specsheet wordmark as home link, catalogue navigation, theme control. Main hierarchy is breadcrumb, page title and description, task controls, data. A persistent unreviewed-pilot notice explains uncertainty without overwhelming results. Use simple category list rows with name, description and count, not marketing cards.

Category desktop: 224–256px filter rail to the left of the results; search/count/column controls above a semantic comparison table. At <=800px filters become a disclosure above results. Horizontal scrolling belongs only to the table wrapper; product column remains readable and names wrap. Select checkboxes and product links are distinct targets. A comparison shelf appears after selection, names selected products, permits removal, explains the 2–4 limit and links to comparison once eligible.

Product: name and identifiers lead, followed by identity caveats and notes. Grouped specification tables pair values with compact, expandable evidence details. Display field-specific citations as field evidence and fallback record citations as context only. Confidence is labeled by scope; legacy record confidence must not appear as verified field confidence. Explicit Unknown, Conflicted, Not yet extracted and Not applicable states are readable text. Lists retain known-empty meaning. Sources use human-readable host/title links, with raw URLs available. Documents and media have honest empty states.

Comparison: 2–4 products within one category, product headers and schema-grouped rows. Highlight differing values with a subtle tint and a text/legend cue; offer differences-only. Unknown and conflicted values remain distinct, never false. On phones the table scrolls horizontally within its own region. Preserve an obvious return to category results.

## Delivery choice
Plain static HTML/CSS/ES modules avoid a framework build dependency for a small read-only catalogue. Python emits versioned JSON into docs/api/v1. Hash routes and relative fetch/asset URLs work both at localhost root and GitHub Pages `/specsheet/` without rewrite rules. No external fonts or services. All user-facing data is escaped or inserted as text; source URLs accept only http(s). Async route changes must not render stale results.

## Verification
Build checks every shipped .js/.mjs and executable inline script with node --check; it fails on any syntax error. Dataset smoke checks every emitted JSON, counts, IDs, schema keys and detail/index agreement. Browser smoke checks nonempty charger rows and Anker search when Playwright is available, plus responsive layout, keyboard access, compare and explicit state behavior during review. Keep tests at port 3999 and test the deployment subpath.

## A4 schema and catalogue behavior

Load the published category schema and every compact index shard for profile-driven categories. Use compact rows for search, filtering, grouping and pagination; fetch full records only for product inspection and comparison. Legacy chargers keep their compatible index. Hide `power-strips-demo` from catalogue navigation and route access; the real power-strip category replaces it in the UI without deleting dataset fixtures.

Keep parent identity explicit. Group configurations using published parent IDs, and link to the parent record for inspection. A family is not a model and a model is not a purchasable configuration. Show configuration labels and differences in indexed facts, with exact configuration links for complete specs. Configure-to-order option axes remain option lists, never invented SKUs. Search and filters operate on the matching records before pagination.

Core facts lead; important and detail tiers use labeled disclosures. Schema groups and labels organize tables and the column chooser. Per-port objects use semantic nested tables with units, while literal port statements stay readable list items. Preserve unknown subvalues and unsupported properties without inventing port capabilities. Conditions, alternatives and inherited provenance accompany the headline value. A missing, conflicted, not applicable or not published fact never becomes “No”.

The comparison shelf precedes results, and pagination limits rendered catalogue rows. The URL preserves search, filters, columns, sort, page and selections through product/comparison return links. Compact action targets meet the 44px project target. Default columns can be restored directly from the grouped chooser.

## Missing products, search misses and corrections

There is no passive search logging, third-party analytics, remote collector or automatic issue creation. A zero-result search offers a product request; readers can also request a missing product from a category. The request is a draft until the reader reviews and submits it on GitHub. Explain at the action that GitHub issues are public and require a GitHub account; readers should include product information only.

Build a transport-independent request payload with `category`, the query as typed, `query_norm`, an optional recognized `identifier_guess`, and the dataset `build`. The current transport is a prefilled GitHub issue form at `shrestha-pranav/specsheet`, using `.github/ISSUE_TEMPLATE/missing-product.yml` and the `missing-product` label. The form has a `payload` field plus optional brand, product URL and context. Do not attach browsing history, identifiers for the visitor, timestamps, IP addresses or unrelated filters. Normalization is for intake deduplication; retain the original spelling separately. Guess an identifier only when its format validates; never claim that a guessed identifier is an established product match.

Field evidence offers a separate correction draft using `field-correction.yml`, with entity ID, field key, shown value and build; the reader supplies the proposed value and evidence URL before submission. Escape display data and URL-encode draft parameters. Opening an external draft sends only that chosen draft to GitHub, so no external request is made merely by searching or viewing a product.

No local miss queue is enabled in this round. A miss is retained only in the current search/URL state; local storage remains reserved for the theme preference. This avoids retaining private queries without consent. A future optional local queue must be explicitly enabled, bounded, inspectable and clearable, with no background upload. Maintainer intake/deduplication and any future server transport are outside this static UI round; maintainers can process deliberately submitted issues using the contract payload.

## Default sort and preview
Default sort is spec coverage (core specs known / core specs) descending, reviewed rows before unreviewed ones, then brand and name: a thin model stub should not outrank a complete record just because its brand sorts first. Preview rows are opt-in (`preview=1` in the URL), badged with the text "Unreviewed candidate" (dashed styling is only reinforcement), and always shown below, never instead of, the accepted value. Preview is strictly additive: every accepted row and fact stays, preview claims attach as candidates with their own source links, preview-only identities are appended, counts derive from the resulting collection, and selections survive toggling (turning preview off removes only preview-only selections, with an explanation).

## Hardware revisions
Model pages with `revisions[]` get a "Hardware revisions" section before Documents: a rule-style table, one row per revision (label links to the revision page), listing only the claims that differ from the model, each with a linked source-tier badge and "(model: x)" when the model has a different value. Empty differs reads "Nothing known beyond the model", never "same". Revision index rows (`kind=revision`) are filtered out of listings and counts; revision pages link back to the model. The preview toggle's brand hint is derived from preview-only rows and omitted when the category has none.

## Trust vocabulary (critique 2, 2026-11-23)
Three distinct states, never blended: "Accepted into catalogue" (a recorded review decision about cited source claims; it is not independent testing), "Unreviewed candidate" (preview claim, no decision), and legacy pilot records (charger category, not reviewed). Source type is a separate axis ("Manufacturer claim", ...). Scope sits beside the value: direct field source, inherited model claim, or record context. A candidate never borrows the accepted value's sources. "Unknown" means no recorded value, never "unverified" and never "No". Blanket "unreviewed" banners must not be applied to categories that have review decisions.

## Search, absence and requests
Search accepts pasted retail titles: model-number-like tokens are extracted client-side, exact identifiers rank first, then same-model-code neighbours, then all-word and partial word matches, each showing why it matched and what identifier still needs checking. Only curated, evidenced aliases may equate marketing names; loose matches are flagged. A failed search states what was searched and never claims absence ("No match for this search"); active-filter exclusions are distinguished and offer Clear filters, per-term broader searches and the unreviewed candidates before any request. Both request entry points read "Prepare GitHub issue draft" with "Public if submitted; GitHub account required. Include product information only." The raw query is passed; only `query_norm` is normalized.

## Models, configurations and differences
Model and family pages are explicitly non-purchasable. The configuration grid carries 2-4 selection controls and "Compare selected configurations"; selected MTMs, model context and preview state survive in URLs and the compare page returns to the model. Configuration identifiers are labelled "MTM / part number" (laptops) or "Model number", not the generic "Model". Tiering may collapse differences but must disclose their existence: the grid shows the most buyer-relevant differing fields from all schema tiers, then "N more differing specifications" in a disclosure, plus a compact CPU / RAM / storage / display / OS / pen summary of recorded values only (never inferred from names). An arbitrary column cut must not imply equivalence. Compare rows are classified by normalized claim meaning (value, qualifier, conditions, alternatives); evidence-only and candidate-only differences are flagged separately and not counted as hardware differences. Empty differences read "No differences among displayed fields" with hidden-tier counts; detailed-field scope persists in the URL (`detail=1`).

## Revisions, grouping, pagination, phones
Revision count and scope sit beside model identity, before specifications, with a jump link; categories whose attributes are revision-level say "No revision-specific evidence recorded" when none is. Result lists offer Flat or Grouped-by-model views; grouping happens before pagination (matching of total configuration counts per group) and flat rows always show the parent link. Pagination keeps focus on the surviving control and announces the page. Phones (<= 800px) merge brand, product and MTM into one sticky identity cell beside Select; comparison keeps a narrow sticky label and one readable product column. Specification wrappers are named, focusable regions.
